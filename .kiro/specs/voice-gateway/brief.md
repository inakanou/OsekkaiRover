# Brief: voice-gateway

## Problem
ロボットの機能は今後増えていく（仕事や生活の補佐）。使う人は、ボタンを押して話しかけるだけで、どの機能にもたどり着けるようにしたい。サンプルでは、聞き取った言葉をおしゃべり機能がゲームへ振り分けていて、入口と会話が混ざっている。

## Current State
- サンプルの `ears.py`:
  - USB マイク（C270）から `arecord` で 5 秒録音する
  - Raspberry Pi 上の faster-whisper（`base`、int8、日本語、VAD、言葉のヒント付き）で文字にする
- サンプルの `chat.py`:
  - ボタンを押すと「なあに？」と聞き、LCD に「ｷｲﾃﾙﾖ」を出し、聞いている間は LED を点ける
  - 聞いた言葉をまず `routine.play_by_words` に渡す（「だるま」などでゲームが始まる）。当てはまらなければ Claude に送る
- 見つかっている問題:
  - 聞き取った子どもの言葉を、ログ（journal）にそのまま出している
  - おしゃべりが無効だと、ボタンの押下が誰にも消費されない

## Desired Outcome
- ボタンを押すと、ロボットが聞く姿勢になり（声・LCD・LED）、話した言葉を文字にする
- 文字にした言葉を、登録された機能のうち当てはまるものへ渡す。各機能は、自分が受け付ける言葉（意図）を自分で登録する
- どれにも当てはまらない言葉は、受け手として登録された機能（`conversation`）へ渡す。受け手がいなければ、やさしく分からなかったと伝える
- 入口は機能の中身を知らない。機能を足しても入口を書き換えない
- 子どもの話した言葉を、ログや記録に残さない
- 振り分けの判定は、偽の聞き取りを使って PC でテストできる

## Approach
`rover-core` の機能として登録し、ボタンとマイクの資源を持つ。聞き取り（音声 → 文字）はポートにし、実機では faster-whisper、テストでは偽物を使う。言葉の登録は、まずキーワードの一致から始め、後で別の判定方法（例: LLM による意図の判定）に差し替えられる形にする。

## Scope
- **In**:
  - ボタンを押して聞く流れ（聞く姿勢の表示、録音、文字にする）
  - 言葉（意図）の登録の口と振り分け
  - 当てはまらない言葉の受け手
  - 利用できる時間帯の扱い（夜は「ねる じかんだよ」）
  - 個人データの扱い（言葉をログに残さない）
  - マイクの設定
- **Out**:
  - Claude との会話（`conversation`）
  - 各機能の言葉の中身（各機能が登録する）
  - 呼びかけの言葉（ウェイクワード）での起動（将来の検討）

## Boundary Candidates
- 聞き取り（音声 → 文字）
- 意図の登録と振り分け
- 聞く姿勢の表示

## Out of Boundary
- 個々の機能の振る舞い
- LLM との会話

## Upstream / Downstream
- **Upstream**: `rover-core`（機能を足す口、ボタン、声、LCD、LED）
- **Downstream**: `conversation`（当てはまらない言葉の受け手）、`daruma-game`（「だるまさん しよう」）、`daily-routine`（任意）、今後の補佐機能

## Existing Spec Touchpoints
- **Extends**: なし
- **Adjacent**: `rover-core`（ボタンの押下を誰が受けるか）、`conversation`

## Constraints
- 音声の文字化は実機の中で行う（音声を外部に送らない）
- Raspberry Pi 5 の CPU で、待たせすぎない速さにする
  - faster-whisper の `base` int8 で、5 秒の音声に 1.5〜3 秒かかる見込み（公表された計測はない）。実機で測り、日本語の精度が足りなければ `small` を検討する
  - 言語は日本語に固定し、VAD を使う。冷却ファンが要る
  - モデルの読み込みに数秒かかるので、起動時に読み込む
