# Brief: rover-core

## Problem
保護者（開発者）は、ロボットに新しい機能を足していきたい。しかしサンプルは、ハードの読み込み・優先順位・保存先がメインループと各モジュールに散らばっている。機能を足すたびに中央を書き換える必要があり、PC ではテストできず、止めたときにモーターが止まらない危険もある。

## Current State
- サンプル（`OsekkaiRover-src.zip`）の `main.py`、`body.py`、`lcd.py`、`voice.py`、`routine.py` の `tick()` が基盤の役割を兼ねている
- 主な問題:
  - SIGTERM を処理しないため、`systemctl stop` で `body.close()`（モーター停止）が走らない
  - 予期しない例外で落ち、10 秒後に systemd が再起動する
  - 複数のスレッドが同時にサーボとモーターを動かす。話す声と LCD 表示が別のスレッドから衝突する
  - 調停に使うフラグ `busy` にロックがない
  - ボタンを押しても、おしゃべりが無効だと押下が消費されない。その間ほかの機能が止まり続ける
  - 設定（`config/local.yaml`）と記録（`data/`）がリポジトリの作業コピーの中にあり、作業ディレクトリもそこへ移動する
  - ハードのライブラリ（picarx、robot_hat、smbus2）をファイルの先頭で読み込むため、PC で読み込めない
  - 時計を差し替えられない
- このリポジトリには、まだ製品のコードがない

## Desired Outcome
- 実機で起動すると、LCD に待機画面（日付・時刻・顔）が出て、ボタンとサーボが反応する
- どの止め方（SIGTERM、SIGINT、例外）でも、モーターは必ず止まり、首は正面に戻る
- 新しい機能は「機能を足す口」に自分を登録するだけで加われる。そのとき優先度と、使う資源（声・画面・モーター・首・LED・ボタン）を自分で申告する。基盤は個々の機能を知らない
- 優先度の高い機能が資源を求めると、低い機能は止まるか中断の通知を受ける
- 設定・記録・キャッシュはリポジトリの外（XDG のディレクトリ）に置く。記録は停電しても壊れない書き方をする
- 判定ロジックは、ハードなしで PC と CI でテストできる。CI に lint とテストのジョブを加える

## Approach
ポートとアダプタ。ハードの操作はインターフェース（ポート）越しにし、実機用のアダプタと、テスト用の偽物を用意する。資源の調停役が、機能ごとの優先度に基づいて資源の取得と解放を管理する。機能は登録の口（プラグインの契約）を実装する。時計は差し替え可能にする。

## Scope
- **In**:
  - 起動・停止・シグナル処理・例外時の安全な停止
  - 設定の読み込みと検証、既定値（設定の見本はリポジトリに、実際の設定はリポジトリの外に置く）
  - 保存の仕組み（壊れにくい書き込み、再起動をまたぐ状態の保存）
  - ハードのポートと実機アダプタ: LCD 1602（文字の変換・中央寄せ・独自文字・バックライト）、声（Open JTalk、キャッシュ、再生）、ボタン（USR と追加ボタン）、LED、サーボ（首・ステアリング）、モーター、基本の動き（うなずく、見回す、眠そう、ダンス。タイヤは設定で許可したときだけ）
  - 資源の調停、機能を足す口、待機画面
  - 開発用の CLI（`--say` など、基盤で完結するもの）
  - systemd のユニット、CI の lint とテスト
- **Out**:
  - 実機への配置と切り戻し（`device-deployment`）
  - 音声の入力と振り分け（`voice-gateway`）
  - カメラ（`presence`）
  - 個々の機能の振る舞い

## Boundary Candidates
- ハードのポートとアダプタ
- 資源の調停と機能の登録
- 設定と保存
- 起動と停止のライフサイクル
- 待機画面

## Out of Boundary
- 日課の判定、あいさつ、会話、ゲーム、ラジコンの振る舞い
- 個々の機能の優先順位（各機能が自分で申告する）
- カメラと音声入力のデバイス

## Upstream / Downstream
- **Upstream**: なし（ハードのライブラリ: picarx、robot_hat、smbus2、Open JTalk、PipeWire）
- **Downstream**: すべてのスペック

## Existing Spec Touchpoints
- **Extends**: なし
- **Adjacent**: `device-deployment`（self-check と systemd のユニットの扱いを分担する）、`voice-gateway`（ボタンの押下を誰が受けるか）

## Constraints
- Python、Raspberry Pi OS（64-bit）、systemd のユーザーサービス
- `picarx` には依存せず、SunFounder の `robot_hat`（GitHub の 2.5.x、2026-09-11 以降）の上に自前のアダプタを書く。サーボの調整値は、リポジトリの外の自前の保存先に置く（picarx の既定 `/opt/picar-x` は root が必要）
- robot_hat は読み込み時に `/proc/device-tree/` を読むので、実機用のアダプタの中だけで読み込む
- Robot HAT のスピーカーは、有効化のピン（v4 は 20、v5 は 12）を立てる必要がある。再生先のデバイスは明示する
- I2C は LCD（0x27）と HAT（0x14）が同じバスを使う。複数のスレッドから書くときはロックする
- CI（x86）でハードなしにテストできること
- 個人の設定と記録をリポジトリに入れない
