# 実機への配置の手順書

開発 PC から実機（Raspberry Pi 5、1 台）に版を入れ、確かめ、だめなら戻す道具 `rover-deploy` の使い方です。
実機は子どもが毎日使っています。入れ替えは、子どもが使っていない時間に行います。

コマンドは、リポジトリの作業コピーの一番上で実行します。

```sh
deploy/rover-deploy <サブコマンド>
```

この手順書では `rover-deploy <サブコマンド>` と書きます。

## 1. 全体の形

### 実機の置き場所

| 場所 | 中身 |
| --- | --- |
| `~/osekkai-rover/repo.git` | リポジトリの bare の写し |
| `~/osekkai-rover/releases/<sha の頭 12 字>/` | 版ごとのディレクトリ（worktree と、版ごとの仮想環境 `.venv`） |
| `~/osekkai-rover/current` | 今の版へのリンク |
| `~/osekkai-rover/tool/` | 開発 PC から写した道具（毎回写し直します） |
| `~/.config/systemd/user/osekkai.service` | 今の版のユニットの写し |
| `~/.local/state/osekkai-deploy/` | 道具の状態・入れ替えの記録・ロック・実機のバックアップ |
| `~/.config/osekkai/`・`~/.local/state/osekkai/` など | 基盤の設定と記録。版の外にあるので、入れ替えても残ります |

### 2 つのサービス

- `osekkai.service`: 新しい基盤のサービスです。`~/osekkai-rover/current` の版を動かします
- `osekkai-rover.service`: サンプル（`~/works/OsekkaiRover` と `~/.venvs/osekkai`）のサービスです。道具はサンプルのファイルを読む・写す・止める・起動するだけで、書き換えません
- 2 つは同時に動きません。`osekkai.service` に `Conflicts=osekkai-rover.service` があり、片方を起動すると、もう片方は止まります

### 普段の版と試しの版

- **普段の版**: 子どもがふだん使う版です。今はサンプルです。`rover-deploy everyday` で決めます
- **試しの版**: `rover-deploy deploy` で入れた、普段の版ではない版です。試しの版は自動で起動する設定にしません
- 普段の版がサンプルの間は、実機を再起動すると、サンプルで立ち上がります
- 試し終わったら `rover-deploy back` で普段の版に戻します

### 版の表示

| 版 | 表示 |
| --- | --- |
| タグ | `v0.2.0` |
| ブランチ | `feat/x@abc1234`（ブランチの名前と、コミットの短い識別子） |
| サンプル | `sample` |

### 終了コード

| コード | 意味 |
| --- | --- |
| 0 | 成功 |
| 2 | 使い方の誤り（サブコマンドや引数の誤り） |
| 10 | 中止。実機は変えていません |
| 11 | 入れた版の確認が失敗し、前の版に戻しました |
| 12 | 前の版の確認も失敗し、サービスを止めました。人の手が要ります（[失敗したときに人がすること](#9-失敗したときに人がすること)） |
| 13 | 接続が切れて、結果が分かりません。`rover-deploy status` で確かめます |

`self-check` は、だめの項目があると 1 で終わります。

## 2. 開発 PC の準備

開発 PC に要るもの: Python 3.11 以上、`git`、`ssh`・`scp`。
道具は標準ライブラリだけで動くので、仮想環境は要りません。

### ssh の接続先

実機の接続先は、リポジトリに書きません。開発 PC の `~/.ssh/config` に別名を作ります。

```
Host rover
    HostName <実機のホスト名か IP アドレス>
    User <実機のユーザー名>
    IdentityFile ~/.ssh/<鍵のファイル>
```

- `<...>` は自分の値に変えます。実際の値は、このリポジトリのどのファイルにも書きません
- 鍵で、パスワードなしにログインできるようにしておきます（`ssh rover true` が問いなしで終わること）
- 実機のログインシェルは、bash など POSIX の sh 系にします（既定の bash のままでよい）。道具はそれを前提に、ssh でコマンドを送ります

### 道具の設定

`~/.config/osekkai-deploy/config.toml` を作ります。

```toml
host = "rover"  # ssh の接続先。~/.ssh/config の別名を勧めます。必須
backup_dir = "~/.local/share/osekkai-deploy/backups"  # 省略できます
repo_url = "https://github.com/<owner>/<repo>.git"  # 省略できます
```

- `host`: 必須です。ない、または設定のファイルがないときは、書き方を表示して終了コード 10 で終わります
- `backup_dir`: 開発 PC にバックアップを受け取る場所です。省略すると `~/.local/share/osekkai-deploy/backups` です。git の作業コピーの中は断ります（バックアップには API キーや記録が入るため）
- `repo_url`: 実機が版を取るリポジトリの URL です。https だけを使えます。省略すると、作業コピーの `origin` から https の形を作ります（`origin` が ssh の別名のときは作れないので、書いてください）
- 設定のファイルを別の場所に置くときは、環境変数 `OSEKKAI_DEPLOY_CONFIG` にその場所を入れます

## 3. 初期設定（provision）

新しい SD カードから実機の環境を作るとき、または足りないものを入れるときに行います。
何度実行してもかまいません。

```sh
rover-deploy provision            # 最初の版は、いちばん新しい vX.Y.Z のタグ。なければ main
rover-deploy provision --ref v0.2.0
```

### 行う手順

済んでいる手順は飛ばし、そのことを表示します。2 回目の実行では、済んだ手順を飛ばし、何も変えません。

- `self_check` は確かめるだけの手順なので、毎回行います
- `secrets` は、`~/.config/osekkai/env` ができるまで、毎回置き場所と作り方を表示します

| 手順 | すること |
| --- | --- |
| `os` | Debian 13（trixie）か 12（bookworm）の aarch64 かを確かめます。違えば何も変えずに中止します |
| `apt` | 要るパッケージ（`git`、`python3-venv`、`open-jtalk` など）のうち、入っていないものを入れます。入れるとカーネルか起動のファイルも新しくなるときは、入れずに止まります（下の「カーネルの更新」） |
| `boot_config` | `/boot/firmware/config.txt` に I2C と音声の行がなければ足します（足す前に写しを取ります）。再起動が要ります |
| `groups` | `gpio`・`i2c`・`audio` と、journal を読めるグループ（`systemd-journal` か `adm`）に入れます。再起動（ログインし直し）が要ります |
| `linger` | ログインしていなくてもユーザーサービスが動くようにします（`loginctl enable-linger`） |
| `layout` | `~/osekkai-rover/` と道具の状態のディレクトリを作ります |
| `voices`・`models` | 声のファイルと顔のモデルのうち、ないものを取ります。取得元と sha256 は道具に決めてあります。同じ名前で中身の違うファイルがあれば、上書きせずに警告します |
| `release` | 版のディレクトリが 1 つもなければ、最初の版を用意し、`current` とユニットを置きます。起動も、自動の起動の設定もしません |
| `reminder` | 戻し忘れのタイマー（`osekkai-trial-reminder.timer`）を置いて有効にします |
| `secrets` | API キーなどの置き場所と、作り方を表示します。ファイルは作りません |
| `self_check` | 新しい基盤の self-check を行い、結果を表示します |

### カーネルの更新

足りないパッケージを入れると、カーネルや起動のファイル（`/boot/firmware`）まで新しくなることがあります。
実機確認で、そのあとの再起動で起動の区画が壊れ、SD カードを作り直しました。
そのため `apt` の手順は、先に試し（`apt-get -s install`）を行い、カーネルや起動のファイルが入るなら止まります。

止まったときは、子どもが使っていない時間に、実機で次を行ってから、もう一度 provision を実行します。

```sh
sudo apt update
sudo apt full-upgrade
sudo reboot
```

再起動の後に立ち上がらなければ、すぐ気づけるように、画面をつないでおくと安心です。

### sudo のパスワード

`apt` などで `sudo` を使います。provision は ssh に端末を割り当てるので、問いが出たら実機のユーザーのパスワードを入力します。
道具はパスワードを扱いません。

### 再起動が要るとき

`boot_config` か `groups` を行ったときは、最後に「再起動が要ります」と出ます。道具は再起動しません。
子どもが使っていない時間に、実機で `sudo reboot` を行います。

### 失敗したとき

失敗した手順の名前と、やり直し方を表示して、そこで止まります（終了コード 10）。
やり直し方のとおりに直してから、もう一度 `rover-deploy provision` を実行します。済んだ手順は飛ばすので、続きから進みます。

### API キーなどの置き場所

API キーなどは、実機の `~/.config/osekkai/env` に、1 行に 1 つ「名前=値」で書きます。
道具はこのファイルを作らず、中も読みません。実機で自分で作ります。

```sh
mkdir -p -m 700 ~/.config/osekkai
touch ~/.config/osekkai/env
chmod 0600 ~/.config/osekkai/env
```

このファイルはリポジトリに入れません。

### self-check の結果

最後に self-check の結果を出します。だめの項目があっても、初期設定は失敗にしません。
「self-check にだめの項目があります」と出たら、`rover-deploy self-check` で項目を確かめます。
サンプルが動いている間は、ハードの項目を確かめません（サンプルとハードを取り合わないため）。

## 4. 入れ替え（deploy）

```sh
rover-deploy deploy v0.2.0        # タグ
rover-deploy deploy feat/x        # ブランチ
```

- 入れられるのは、GitHub に push 済みのコミットだけです。手元だけのタグや、push していないコミットは断ります
- 同じ名前のタグとブランチがあれば、タグを使います
- 最初に「今の版: ... / これからの版: ...」を、実機を変える前に表示します
- 普段の版と同じ版を入れたときは、普段の版として入れます（自動の起動を設定します）。ほかは試しの版です

### 流れ

1. 道具を実機に写します。つながらなければ中止（10）
2. 事前の確認をします。中止の理由があれば表示して中止（10）。実機は変えていません
3. バックアップを作り、開発 PC に受け取ります。受け取れなければ中止（10）
4. 実機の側で入れ替えを始めます。ssh が切れても、実機の側で最後まで進みます
5. 手順ごとの結果（準備・安全の確認・切り替え・起動・確認など）を表示し、最後に結果と終了コードを出します

### 事前の確認で中止したとき

| 表示 | 対処 |
| --- | --- |
| 実機が走行中です | 止まってからやり直します |
| 実機で作業中の機能があります（作業中の機能: ...） | その機能が終わってからやり直します |
| 実機のサービスの様子を確かめられません | 起動の直後や停止の途中のことがあります。少し待ってからやり直します |
| サンプルが動いています | 子どもが使っていないことを確かめてから、`rover-deploy stop` で止めて、やり直します |
| 実機の空き容量が足りません | 実機の空きを作ってからやり直します |
| 今の版に手の変更があります | 実機の `~/osekkai-rover/current` で手で変えたファイルがあります。実機で `git -C ~/osekkai-rover/current status` で確かめ、要らなければ捨ててからやり直します |
| 前の入れ替えが途中で終わっています | `rover-deploy status` で確かめ、`rover-deploy back` で普段の版に戻します |
| ほかの入れ替えなどが実機で動いています | 終わってからやり直します |

### バックアップ

- 入れ替えのたびに、基盤の設定・記録・データとサンプルのデータをまとめ、開発 PC の `backup_dir/<識別子>/` に受け取ります。表示は場所と大きさだけです
- 実機にも、新しい順に 5 つ残します
- 初めて新しい基盤の版を入れるときは、サンプルのバックアップ（作業コピー全体・ユニット・パッケージの一覧）も受け取ります。受け取れたことを実機に記録し、2 回目からは作りません
- バックアップには API キーや記録が入ります。ファイルは本人だけが読める権限（0600）で置きます。作業コピーの中に置いたり、人に渡したりしないでください

### 切り戻し

入れた版の確認（起動・self-check・30 秒動き続けること・版のログ）が失敗したら、道具は自動で前の版に戻し、失敗した確認の名前を出します（終了コード 11）。
前の版の確認も失敗したら、両方のサービスを止めて安全停止を行います（終了コード 12）。そのときは [失敗したときに人がすること](#9-失敗したときに人がすること) を見ます。

### 接続が切れたとき（13）

「接続が切れました。結果は rover-deploy status で確かめてください」と出て、終了コード 13 で終わります。
実機の側では入れ替えが続いています。少し待ってから `rover-deploy status` で結果を確かめます。
`rover-deploy log` で手順ごとの結果も見られます。

## 5. 試しの版から普段の版に戻す（back）

```sh
rover-deploy back
```

- 普段の版に戻します。流れは入れ替えと同じです（事前の確認・バックアップ・切り替え・確認）
- 普段の版がサンプルのとき: `osekkai.service` を止め（止めるときに安全停止が動きます）、サンプルを起動します。確認は「30 秒動き続けること」だけです
- もう普段の版（サンプル）で動いていれば、何も変えずに 0 で終わります
- 前の入れ替えが途中で終わっていたときも、`back` で普段の版に戻して片付けます

### 普段の版の決め方（everyday）

```sh
rover-deploy everyday v0.3.0      # タグを普段の版にする
rover-deploy everyday sample      # サンプルを普段の版にする
```

- 普段の版に使えるのは、タグか `sample` だけです。ブランチは `deploy` で試しの版として入れます
- `everyday` は記録するだけで、入れ替えはしません。続けて `rover-deploy back` で入れ替えます
- 普段の版が新しい基盤の版になると、`back` で `osekkai.service` を自動で起動する設定にし、サンプルのユニットの自動の起動を外します。サンプルのファイルは残します

### 戻し忘れの知らせ

- 版を入れた後、LCD に版の知らせが少しの間出ます。1 行目は版の表示、2 行目は `ふだんのばん`（普段の版）か `ためし ふだん:<普段の版>`（試しの版）です
- 試しの版を入れてから 3 時間を過ぎると、LCD の 2 行目に `ためしのばん もどしてね` が出続けます（戻し忘れのタイマーが、起動の 10 分後と 1 時間ごとに確かめます）。普段の版に戻すと消えます
- 開発 PC でも、どのサブコマンドでも最初に「試しの版が 3 時間以上入っています。rover-deploy back で戻してください」と警告します

## 6. バックアップから戻す（backups・restore）

```sh
rover-deploy backups                             # 実機のバックアップの一覧（新しい順）
rover-deploy restore 20261104T210000Z            # 実機のバックアップから戻す
rover-deploy restore --file <開発 PC のファイル>   # 開発 PC に受け取ったバックアップから戻す
rover-deploy restore 20261104T210000Z --include-sample   # サンプルのデータも戻す
```

- 戻すのは、基盤の設定・記録・データです。サンプルのデータは `--include-sample` のときだけ戻します
- 実機の道具は、安全の確認 → 今の状態のバックアップ → 動いているサービスを止める → 戻す → 止めたサービスを起動する、の順に行います。戻す前の状態のバックアップの識別子も表示します
- 走行中・作業中のときは中止します（10）
- サンプルが動いているときは中止します。子どもが使っていないことを確かめてから `rover-deploy stop` で止め、もう一度 `restore` を実行します。止めてから戻したときは、サービスは止まったままなので、最後に `rover-deploy back` で普段の版を起動します
- 戻した後にサービスを起動できなければ、終了コード 12 です。[失敗したときに人がすること](#9-失敗したときに人がすること) を見ます
- サンプルのバックアップ（`sample-<識別子>.tar.gz`）は、一覧と復元の対象ではありません。開発 PC に受け取ったファイルを、人が見て使います
- `--file` で送ったファイルは、実機の `~/.local/state/osekkai-deploy/backups/uploaded-<識別子>.tar.gz` に残ります。世代の削除の対象ではないので、要らなくなったら実機で消します

## 7. self-check

```sh
rover-deploy self-check
```

- 実機の今の版（`~/osekkai-rover/current`）で self-check を行い、項目ごとに「よい・だめ・飛ばした」を出します。だめがあれば終了コード 1 です
- 実機で直接行うときは、`~/osekkai-rover/current/.venv/bin/python -m osekkai --self-check` です（`--json` で JSON、`--no-hardware` でハードの項目を飛ばします）
- 新しい基盤のサービスが動いている間は、ハードの項目はハードに触らず、サービスの報告で判定します
- サンプルが動いている間は、ハードの項目を確かめません
- **self-check の最中に `osekkai.service` を起動しないでください。** self-check はハードを使う間、単一の実行のロックを持ちます（声の合成で最大 40 秒）。その間に起動したサービスは「すでに動いています」（75）で終わり、起動し直しません。起動してしまったときは、self-check が終わってから起動し直します

## 8. 版の確認と記録（status・log）

```sh
rover-deploy status
```

- 動いている版・普段の版・試しの版か（入れてからの時間）・最後の入れ替えの結果と時刻を出します。実機は変えません
- 入れ替えが途中で終わっていれば、そのことと `back` を案内します
- 実機の LCD でも、版を入れた後に版の知らせが少しの間出ます。基盤の journal には、起動のときに `版: <版の名前>` の行が出ます

```sh
rover-deploy log                      # 最新の入れ替えの記録
rover-deploy log 20261104T210000Z     # 指定した入れ替えの記録
rover-deploy log --list               # 記録の識別子の一覧（新しい順）
```

記録は実機に新しい順に 50 件残ります。表示は手順の名前と結果だけです。

## 9. 失敗したときに人がすること

### 終了コード 12 のとき

12 は「サービスを止めた。人の手が要る」の意味です。次のどれかです。

- 入れた版も前の版も確認が失敗し、両方のサービスを止めた
- `restore` の後に、止めたサービスを起動できなかった
- `restore` が途中で止まり、その残りを片付けられなかった（「途中で止まった復元を片付けられません」）
- `stop` で、モーターが止まったことを確かめられなかった（版がない、または安全停止が失敗した）

次の順に行います。

1. 実機のモーターが止まっていることを、目で確かめます（下の「モーターを確実に止める方法」）
2. `rover-deploy status` と `rover-deploy log` で、どの手順が失敗したかを見ます
3. 実機の journal で、失敗の様子を見ます（下の「journal の見方」）
4. 直せたら、`rover-deploy back` で普段の版に戻します

### モーターを確実に止める方法

上から順に試します。

1. 開発 PC で `rover-deploy stop`。両方のサービスを止め、安全停止を厳しい判定（`--strict`）で行います。0 ならモーターの停止まで確かめられています
2. 実機にログインして、両方のサービスを止めます
   ```sh
   systemctl --user stop osekkai.service osekkai-rover.service
   ```
   片方のユニットがないときは、systemctl がそのユニットの誤りを出します。それでも、もう片方は止まります
3. 実機で安全停止を直接行います。0 で終わればモーターを止められています（ほかが HAT を使っているときなど、ハードに触れなかったときは 1 です）
   ```sh
   ~/osekkai-rover/current/.venv/bin/python -m osekkai.core.safe_stop --strict
   ```
   新しい基盤の版がまだない（`~/osekkai-rover/current` がない）ときは、この手順は使えません。4 に進みます
4. 最後の手段: 実機の電源を切ります。Robot HAT の電源スイッチを切ります（HAT のマイコンは、プロセスが落ちてもモーターの出力を保つことがあるため、HAT の電源を切ります）

### journal の見方

この実機には利用者ごとの journal がなく、`journalctl --user` では読めないので、次の形を使います。

```sh
journalctl --user-unit=osekkai.service -b                  # 新しい基盤（今回の起動から）
journalctl --user-unit=osekkai-rover.service -b            # サンプル
journalctl --user-unit=osekkai-trial-reminder.service -b   # 戻し忘れの確認
```

読めないときは、利用者が journal を読めるグループ（`systemd-journal` か `adm`）に入っているかを `id` で確かめます。入っていなければ `rover-deploy provision` を実行し、ログインし直します。

### 道具の状態のファイルが読めないとき

「実機の道具の状態のファイルが読めません」と出たら、`~/.local/state/osekkai-deploy/state.json` が壊れています。
実機で、壊れたファイルを別の名前に移します。

```sh
mv ~/.local/state/osekkai-deploy/state.json ~/.local/state/osekkai-deploy/state.json.broken
```

ファイルがなくなると、道具の状態は既定に戻ります。

- 普段の版は、サンプルの作業コピーがあればサンプルになります。タグを普段の版にしていたときは、`rover-deploy everyday <タグ>` で決め直します
- 次の入れ替えは初回と同じ扱いになり、サンプルのバックアップをもう一度受け取ります

その後、`rover-deploy status` で確かめます。

## 10. 注意

- **実機で `XDG_*` の環境変数を変えないでください。** ssh から呼ぶ道具と、切り離して動く入れ替えとで、ロックや状態の場所がずれます。`restore --file` も、実機の `XDG_STATE_HOME` が既定であることを前提にしています
- 実機のログインシェルは、bash など POSIX の sh 系にします
- 実機の利用者は、journal を読めるグループ（`systemd-journal` か `adm`）に入っている要があります。入れた後の確認で、版のログを journal から読むためです
- **分かっている穴**: 普段の版が新しい基盤の版のときに試しの版を入れると、`current` とユニットが試しの版を指すので、実機を再起動すると試しの版で立ち上がります。「再起動すれば普段の版に戻る」は、普段の版がサンプルの間だけ成り立ちます。普段の版を新しい基盤の版にする前に直します。それまでは、試し終わったら必ず `rover-deploy back` を行います
- `restore --file` で送った `uploaded-<識別子>.tar.gz` は、実機に残ります。要らなくなったら実機で消します
- バックアップ・入れ替えの記録・self-check の結果は、リポジトリの作業コピーの中に置きません。接続先の値・API キー・個人の設定はコミットしません
